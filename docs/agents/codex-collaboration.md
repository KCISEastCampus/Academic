# Academic：通过 GitHub 接力 Codex 任务

状态：协作方案草案。本文定义建议流程；不会自动改变仓库权限、分支保护或自动检查。

## 目标与分工

每位同学在自己的电脑上使用自己的 GitHub 和 Codex 登录。代码、任务要求和交接状态通过 GitHub 同步。任务运行的用量按执行者的 Codex 登录方式与工作区规则计算。

| 角色 | 职责 |
| --- | --- |
| 项目负责人 | 拆分任务、确定内容标准、审查成果、决定合并与发布 |
| 任务执行者 | 领取任务、在独立分支完成工作、保存进度和交接记录 |
| 审查者 | 独立核对数学、中文表达、页面效果及检查记录 |

执行者可以调度自己的子代理；执行者仍负责复核并交付。个人 Codex 的聊天和记忆只作为补充资料；项目要求必须能从仓库和 Issue 中读到。

## 一次性准备

1. 负责人邀请同学作为仓库协作者，授予完成工作所需的 Write 权限。无需 Admin。若采用 fork，则接力者将接手分支推送到自己的 fork 并开新 PR，关联原 PR。
2. 同学安装 Git、GitHub CLI、Codex，以及 README 所列的 Ruby/Bundler；使用自己的账号登录。按 Gemfile.lock 安装依赖，不照搬另一台电脑的安装路径。
3. 克隆 Academic，在 Codex 中打开本地项目。
4. 把数学内容和双语规范写入仓库的指导文档，并在 AGENTS.md 中引用本流程及内容规范。保持文档简短；任务进度放在 Issue 中。
5. 配置 main 的保护：要求 PR、至少一位其他人的审查、必要检查通过、讨论解决；禁止强制推送和删除。确认管理员是否也受约束。实际可用选项取决于仓库和 GitHub 套餐。
6. 给执行者明确授权范围：可以提交和推送自己的任务分支，可以开 Draft PR、更新本任务的进度记录；合并 main 与正式部署由负责人决定。

第 6 项应由各自的人类用户明确授权给各自的 Codex。仓库文档不会自动获得跨账号的发布授权。

## 日常流程

1. **建任务**：一项任务对应一个 Issue。写明目标、允许改动的文件、资料来源、完成条件和依赖任务；沿用 ready-for-agent 等现有标签。
2. **领取**：将 Issue 指派给执行者。开始前查看指派、最新进度和关联 PR，防止两个人同时接手。
3. **建分支**：从最新 main 建立 codex/<issue-number>-<topic> 分支。依赖尚未合并的改动时，在 Issue 中注明依赖分支和基准 commit。
4. **开展工作**：一个分支同一时间只有一位主要执行者。不同人员并行处理不同章节；共用导航、布局和样式的修改单独协调。
5. **保存进度**：完成一个可描述的阶段后提交并推送。尚未完成也可以保存，但保持 Draft PR，并说明哪些部分不能合并。
6. **审查**：完成后转为待审查状态。负责人用自己的 Codex 复核差异，老师或学生审阅页面，执行者修正反馈。
7. **交付**：负责人批准合并；正式部署按现有流程运行。确认部署结果后关闭 Issue。发现新问题另建任务，保留原任务的结果记录。

合并会更新 main；当前 pages.yml 会在 main 推送时触发正式站点部署。因此日常进度保存到任务分支。

## 额度不足或临时换人

1. 原执行者停止所有会修改该任务文件的代理。
2. 提交并推送当前分支。核对远程分支 commit 与交接记录一致。
3. 更新 Issue 的交接记录和负责人；代码状态以 commit 为准。
4. 新执行者拉取同一任务分支，在自己的 Codex 中开新会话，读取 AGENTS.md、Issue 和交接记录。
5. 新执行者先检查实际文件与记录是否一致，再继续工作；保留已有提交，不强制推送改写共同历史。

若原执行者尚未保存并推送，本地改动不会随 GitHub 拉取出现。无法联系原执行者时，负责人应先核对最后的远程 commit，再决定从该检查点恢复，并记录可能遗漏的本地进度。

如果采用 fork，原 PR 的源分支可能不允许新执行者推送。使用新执行者的分支和 PR 接续，互相链接，并说明旧 PR 如何处理。

```text
Issue 与 PR：

资料链接：

```

## Academic 内容的完成条件

- 中文使用自然的华语数学表达，首次出现的专业术语附英文原词。
- 题干保留英文，中英文公式和答案一致；翻译不能改变定义域、分支、区间或题目条件。
- 官方例题或改编方法注明出处；原创、改编题明确标注，不能冒充官方题目或分值。
- 从官方课程大纲确认范围，并参考官方评分细则；解答需独立核算。
- 检查双语页面元数据、语言切换、页内定位、折叠提示与解答、公式渲染和图像。
- 在任务明确授权验证后，完成构建和针对变更的检查；报告实际结果与未检查项。
- 审查记录对应最终 commit。之后又修改内容，需要重新检查受影响的部分。

## 长期维护与自动检查

优先复用仓库现有的 GitHub Actions。普通 Jekyll 构建和脚本检查无需消耗 Codex 模型用量，但会使用 GitHub Actions 的运行资源；两者的额度分别管理。

目前仓库的 PR 工作流包含 Markdown 检查和链接检查，链接检查允许失败；Jekyll 构建在正式部署工作流中。建议后续补充 PR 阶段的 Jekyll 构建，以及适用的双语一致性检查。先确认检查可靠、覆盖新课程，再设为合并的必过条件。

机器检查不能证明数学答案正确，数学审查仍由执行者与审查者完成。

预览先在执行者本机运行，提交截图和已检查的页面地址。现有局域网预览只适用于同一网络。需要让校外老师审阅时，另行配置 PR 预览；保持预览与正式部署分开，并注明预览对应的 commit。

定期由负责人整理待办列表、关闭重复任务、检查长期无人接手的任务。只有多人频繁协作后，再增加项目看板或自动指派；两人接力用 Issue、分支和 PR 即可。

## 给接手者的 Codex 开场指令

将占位内容替换为真实 Issue 和分支。

```text
请接手 Academic 的 GitHub Issue #<编号>，任务分支为 <分支>。
先读取 AGENTS.md、docs/agents/codex-collaboration.md、Issue 的目标与最新交接记录，
核对当前 commit 和实际文件，简要说明已完成、未完成与本次工作范围，再继续。
中文使用自然的华语数学表达，专业词汇首次出现附英文原词；保留英文题干和公式。
只修改任务允许的文件，遵循 Issue 的完成条件与已授权的检查要求。
若我已授权提交和推送，请按阶段保存到任务分支并更新交接记录。
额度不足或停止前，优先保存进度、说明下一步，并停止相关子代理。
```

## 本轮交接的起点

当前 FP2.8、FP2.9 的中英文课程及双曲函数图像已经写入本地并完成本地构建。它们以及双语界面配套尚有未提交的文件，工作区还包含其他任务的改动。

首次交接应先核对远程 main，整理“课程内容 + 必要双语支持”的独立分支，列清依赖和已检查项，避免混入其他任务文件。获得发布授权后，推送该分支并建立 Draft PR 和交接任务；同学从该分支开始。
